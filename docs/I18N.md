# Internationalization

Notka ships in three locales:

| Code | Language | Role |
| --- | --- | --- |
| `en-US` | American English | **Source of truth.** Defines the `Messages` type and the key set. |
| `en-GB` | British English | Spelling, date, and number conventions. Same wording otherwise. |
| `pl` | Polish | Full translation, with correct `Intl.PluralRules` branches. |

## Where the pieces live

```
frontend/src/entity/locales.ts                 supported locale codes + Accept-Language matching
frontend/src/boundary/i18n/index.ts            t(), tError(), locale detection, plural selection
frontend/src/boundary/i18n/format.ts           localized date/time output
frontend/src/boundary/i18n/locales/en-US.ts    source-of-truth catalogue (defines MessageKey/Messages)
frontend/src/boundary/i18n/locales/en-GB.ts    British English overrides
frontend/src/boundary/i18n/locales/pl.ts       Polish catalogue
frontend/src/boundary/i18n/types.ts            MessageValue / PluralCategory
```

`en-US` is a flat object of dot-separated keys:

```ts
'card.changeColor': 'Change color',
'card.daysLeft': { one: '{count} day left', other: '{count} days left' },
```

`MessageKey` is `keyof typeof enUS`, and `Messages` is a mapped type over those keys, so a catalogue
that forgets a key or invents one fails `pnpm run check`. There is no runtime fallback to hide a
missing translation.

## Using it

```svelte
<script lang="ts">
  import { t, tError } from '../i18n';
</script>

<button title={t('card.archive')}>{t('card.archive')}</button>
<p>{t('card.daysLeft', { count: 3 })}</p>
```

`t()` reads the reactive `ui.locale` value, so a language change re-renders every component that
calls it, with no page reload.

### Plurals

A message value may be a string or a map of `Intl.PluralRules` categories. When `params.count` is
present, the runtime selects the branch with `new Intl.PluralRules(locale).select(count)`.

Polish needs this: `1 dzień`, `2 dni`, `5 dni` are three different categories
(`one`, `few`, `many`).

### Dates and numbers

Never call `toLocaleDateString()` without arguments. Use the helpers in
`boundary/i18n/format.ts` (`formatEditedAt`, `formatDeletedAt`, `formatDaysLeft`,
`formatFullTimestamp`), which read the active locale. Pure calculations such as
`daysUntilPurge` stay in `entity/format.ts` and take no locale.

## Locale selection

1. `localStorage['notka.locale']` when it holds a supported code.
2. Otherwise `navigator.language`, matched with `entity/locales.ts:matchLocale`:
   `pl-PL → pl`, `en-GB → en-GB`, `en-AU → en-US`, anything else → `en-US`.
3. The choice is changed in **Settings → Language** and persisted.

The active locale is written to `<html lang>` and sent on every API request as `Accept-Language`.

## API errors

The backend never translates. Every error response carries a stable key:

```json
{ "error": { "code": "CONFLICT", "key": "share.already_shared",
             "message": "This note is already shared with bob@example.com",
             "params": { "email": "bob@example.com" } } }
```

`tError()` looks up `errors.<key>` in the active catalogue and substitutes `params`. The English
`message` is only shown when a key is unknown to the running build (i.e. the backend is newer than
the frontend), which is a development-only situation.

The full key list is in `docs/API.md`; the catalogue entries are the `errors.*` block of each locale
file.

## Adding a string

1. Add the key to `en-US.ts`.
2. Add the same key to `en-GB.ts` (only if British English differs) and to `pl.ts`.
3. Use it through `t()`.
4. Run `cd frontend && pnpm run check`.

## Adding a locale

1. Append the code to `LOCALES` in `entity/locales.ts` and extend `matchLocale`.
2. Add `locale.<code>` to every catalogue.
3. Create `boundary/i18n/locales/<code>.ts` typed as `Messages`.
4. Register it in the `CATALOGUES` map in `boundary/i18n/index.ts`.
